# Skill: New Change

## Input (from user)
- **Change Number**: e.g., `CHG0440001`
- **Short Name**: e.g., `PRICING_FIX` (uppercase, underscores, no spaces)
- **Functional Document**: The functional specification provided by the business analyst (attached as file, pasted text, or PDF content)

The folder will be created as: `.kiro/specs/{CHG_NUMBER}_{SHORT_NAME}/`

## Procedure

1. Validate input:
   - Change number must match pattern `CHG\d{7}`.
   - Short name must be uppercase alphanumeric with underscores only.
   - Target folder must NOT already exist.

2. Create `.config.kiro`:
   ```json
   {"specId": "<generated-uuid>", "workflowType": "design-first", "specType": "feature"}
   ```

3. Create minimal `requirements.md` (placeholder for Kiro spec recognition):
   ```markdown
   # Requirements: {CHG_NUMBER} — {SHORT_NAME}

   ## Introduction
   [To be derived from design.md by #plan]

   ## Requirements
   [To be generated by #plan after design is approved]

   ## Verification Log
   [Append-only audit trail from #verify]
   ```

4. Absorb the functional document and produce `design.md`:
   - Read the functional document thoroughly
   - Extract the business problem, process flow, and technical requirements
   - Research the SAP system if needed (use SAP MCP tools to understand existing objects)
   - Generate `design.md` with the following structure:

   ```markdown
   # Design: {CHG_NUMBER} — {SHORT_NAME}

   ## SAP Context
   - WRICEF ID: [extracted or ask user]
   - Target Package: [extracted or ask user]
   - Transport Request: [to be assigned]

   ## Overview
   [Technical approach summary based on the functional document]

   ## Architecture
   [How objects interact — Mermaid diagrams if helpful]

   ## Object Breakdown
   | # | Object Type | Object Name | Package | Action | Description |
   |---|-------------|-------------|---------|--------|-------------|
   [One row per ABAP object to create/modify]

   ## Design Decisions
   ### Decision N: [Topic]
   **Choice**: [what]
   **Rationale**: [why]
   **Alternatives considered**: [rejected options]

   ## Approval
   Status: PENDING — reply `DESIGN_APPROVED` to authorize planning.
   ```

5. Report success and next steps.

## Next steps (inform user)
After scaffolding, remind the user:
- Review `design.md` — it contains the initial technical approach based on the functional spec.
- Reply `DESIGN_APPROVED` to authorize the next step.
- Then run `#plan` to refine the design, derive requirements.md, and generate tasks.md.

## Object Planning Rules (apply when writing design.md)

Only plan objects available on ECC 7.5 EHP8:
- Programs/Reports, Includes
- Classes (ZCL_*), Interfaces (ZIF_*)
- Function Modules / Function Groups
- SE11 Tables, Structures, Data Elements, Domains, Table Types, Search Helps, Lock Objects
- Classic BAdI implementations, User-Exits, Enhancement Implementations
- SAPscript / Smartforms / Adobe Forms
- Transactions (SE93)

Do NOT plan: AMDP, RAP behavior definitions, service bindings, Fiori annotation-driven UIs, or CDS views relying on HANA-specific functions/annotations (OLAP, code pushdown). Classic CDS view entities without HANA-specific features may be planned when appropriate.

## Safety
- Never overwrite an existing CHG folder.
- Never create outside `.kiro/specs/`.
- Do NOT create VISION.md, ROADMAP.md, WRICEF.md, or micro-specs/ folder.
